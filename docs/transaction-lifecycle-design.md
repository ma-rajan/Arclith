# Configuration transaction lifecycle design

This document records the Phase 40 audit of the existing configuration lifecycle and later lock and journal work. Phase 41 added the lock helper, Phase 42 integrated it around apply/apply-new, restore, uninstall, and prune transactions, Phase 43 added journal primitives, Phase 44 integrated v1 target checkpoints with apply/apply-new, Phase 46 added v2 checkpoints and restore integration, and Phase 47 integrated v1 target checkpoints with uninstall and prune. Arclith does not implement automatic recovery after process termination or power loss.

Each mutating transaction acquires the per-home helper lock before entering its implementation and retains it through state reads, target changes, manifest writes, rollback, and return cleanup. The lower-level `config_state_save` function does not acquire a nested lock; its current mutation callers are inside these locked transactions. Read-only and dry-run commands remain unlocked. The helper serializes cooperating Arclith processes only; the baseline line references and lifecycle observations below remain tied to Phase 40.

The managed deployment state remains `~/.local/state/arclith/deployments.v1` (`ARCLITH_STATE|1`, mode 600 in a mode 700 directory). Its existing M/B records remain the authority for which files Arclith manages and which backups it trusts. The transaction journal described below records only a transaction summary; it is not authorization to modify a target or artifact.

## Phase 43 journal foundation

The deployment manifest format remains unchanged. Journal records are stored beneath `~/.local/state/arclith/transactions/<id>.v1`, one record per transaction, in a mode-700 directory. The identifier is 32 lowercase hexadecimal characters generated from 16 bytes of `/dev/urandom`; collisions are refused. Each mode-600 record has exactly seven ordered lines:

```text
ARCLITH_TXN|1
ID|<32 lowercase hex characters>
OPERATION|<apply|apply-new|restore|uninstall|prune>
COMPONENT|<lowercase component identifier>
STATE|<lifecycle state>
CREATED_UTC|<YYYY-MM-DDTHH:MM:SSZ>
UPDATED_UTC|<YYYY-MM-DDTHH:MM:SSZ>
```

The parser requires the exact line count and field order; validates the version, operation, component, identifier, state, canonical UTC timestamps, owner, mode, link count, file type, and a 1 KiB record-size limit; and rejects binary, malformed, or unsupported records. It parses data only and never evaluates or sources journal contents. It stores no paths, target contents, credentials, or free-form diagnostics. Invalid records are not repaired or deleted. Journal create and transition calls require the current Bash process to hold the existing per-home lock for the same canonical home. A single-record read validates one atomic snapshot and may be stale if a writer updates it concurrently; readers needing a consistent set of records must use the same lock.

### State machine

```text
PREPARING -> PREPARED -> APPLYING -> COMMITTING -> COMPLETE
     |           |          |          |
     +-----------+----------+----------+-> ROLLING_BACK -> ROLLED_BACK
     |           |          |          |                    |
     +-----------+----------+----------+--------------------+-> UNCERTAIN
```

Valid transitions are `PREPARING -> PREPARED`, `PREPARED -> APPLYING`, `APPLYING -> COMMITTING`, and `COMMITTING -> COMPLETE`. Each of those four nonterminal states may also transition to `ROLLING_BACK` or `UNCERTAIN`; `ROLLING_BACK` may transition to `ROLLED_BACK` or `UNCERTAIN`. `COMPLETE`, `ROLLED_BACK`, and `UNCERTAIN` are terminal. The primitives enforce these transitions but do not assert that operations actually completed or that rollback is safe.

Journal writes use a restrictive temporary file in the same transaction directory, validate the serialized temporary record, then call `mv -fT` to atomically replace the destination on the same filesystem. A failed serialization or rename removes only that write's temporary file and leaves the prior valid record in place. This relies on local Linux/GNU utility behavior and the existing cooperative per-home lock; it is not a defense against non-cooperating same-user filesystem races. No file or directory `fsync` is performed, so rename atomicity is not power-loss durability.

Phase 43 alone added no production lifecycle journal writes. Phase 44 integrated v1 target records with apply/apply-new. Phase 46 added v2 restore records. Phase 48 adds read-only enumeration and validation; no phase adds automatic recovery, replay, or journal cleanup. A journal state is descriptive metadata, not proof that a target should be overwritten, restored, or deleted.

## Phase 44 target checkpoints

The Phase 43 transaction record remains unchanged. Each selected apply/apply-new destination has one atomic mode-600 record in `transactions/<transaction-id>.targets/<six-digit-index>.v1`, beneath a mode-700 directory. The version 1 target record contains:

```text
ARCLITH_TARGET|1
TRANSACTION|<32 lowercase hex characters>
OPERATION|<apply|apply-new>
COMPONENT|<lowercase component identifier>
INDEX|<six decimal digits>
TARGET|<validated home-relative registered target>
ORIGINAL|<yes|no>
BACKUP|<8-character backup ID|->
STATE|<target lifecycle state>
UPDATED_UTC|<YYYY-MM-DDTHH:MM:SSZ>
```

The transaction ID and numeric index alone form the checkpoint path. The target path must pass the existing safe-relative-path and registered-component target checks. A backup reference is only an opaque validated Arclith backup ID; it does not grant authority to restore that artifact. The existing backup file, file checks, and rollback implementation remain authoritative.

Target states and allowed transitions are `PLANNED -> STAGED -> MUTATION_INTENT -> APPLIED`. `PLANNED` and `STAGED` can reach `NOT_MUTATED` or `UNCERTAIN`; `MUTATION_INTENT` can reach `APPLIED`, `ROLLBACK_INTENT`, `NOT_MUTATED`, or `UNCERTAIN`; `APPLIED` can reach `ROLLBACK_INTENT` or `UNCERTAIN`; and `ROLLBACK_INTENT` can reach `ROLLED_BACK` or `UNCERTAIN`. `ROLLED_BACK`, `NOT_MUTATED`, and `UNCERTAIN` are terminal states. `NOT_MUTATED` means Arclith did not confirm performing the target replacement; it is not a statement about changes by non-cooperating processes. A `MUTATION_INTENT` left on disk can mean the rename did or did not happen. Target records must agree with their transaction's ID, operation, and component and are updated under the existing per-home lock.

For apply/apply-new, the transaction and all `PLANNED` target records are written before target parent creation, staging, or backup creation. A verified existing-target backup ID is attached while still `PLANNED`. After source staging, the target becomes `STAGED`. The transaction advances to `PREPARED` and `APPLYING`; each `MUTATION_INTENT` is persisted before its destination rename, and `APPLIED` only after the rename reports success. `COMMITTING` is written after every target is confirmed applied and before the deployment manifest update; `COMPLETE` is written only after that manifest save succeeds.

On a failure before any replacement, staged records are marked `NOT_MUTATED` where those writes succeed. After partial replacement, existing rollback runs in reverse order. It writes `ROLLBACK_INTENT` before restoring/removing a target and `ROLLED_BACK` only after the existing rollback path confirms success. A rollback failure, checkpoint write failure, or unclear outcome leaves `UNCERTAIN` when that update can be persisted. If journal storage itself is unavailable, the last saved checkpoint can remain stale; the command reports the failure and does not claim a later checkpoint succeeded. A process kill can occur between any filesystem action and checkpoint, so neither target records nor the transaction record constitute a recovery protocol.

Apply/apply-new are integrated because they share an established all-target staging and reverse-order rollback flow. Restore uses the v2 source/rollback backup references and its existing single-target replacement/rollback flow. Uninstall and prune use v1 records because one opaque `BACKUP` reference is sufficient for each target's recovery copy. They checkpoint `PLANNED` before backup creation, attach the verified backup ID while still planned, then checkpoint `STAGED`. After the transaction enters `APPLYING`, already-missing targets become `ALREADY_ABSENT`; modified or otherwise preserved inspectable targets become `NOT_MUTATED`. A deletion gets `MUTATION_INTENT` immediately before `rm` and `APPLIED` only after the target is confirmed absent. `COMMITTING` precedes clearing final ownership entries, and `COMPLETE` follows a successful final manifest save. The initial backup-registration save also occurs after entering `APPLYING` and before any target deletion. Failure there prevents deletion.

On deletion, checkpoint, or final-manifest failure, the existing flow restores the prior ownership state and best-effort restores deleted targets from their recovery copies. `ROLLBACK_INTENT` precedes each rollback replacement and `ROLLED_BACK` follows content verification; unresolved persistence or rollback outcomes leave the transaction `UNCERTAIN` when possible. A failed final `COMPLETE` write leaves the completed file and manifest changes in place and reports failure/uncertainty. Prune preserves its existing partial-success behavior: eligible stale files can be removed and the transaction completed while conflict entries remain owned and the command exits nonzero. A candidate classified inaccessible is not checkpointed because the code cannot determine its original presence without crossing the safety boundary; it remains preserved, and prune's conflict status reports it. Preview and dry-run paths return before journal creation; restore has confirmation but no dedicated dry-run mode. The existing lock remains held through transaction checkpoints, manifest writes, and rollback. These are command-level tests, not process-kill or power-loss simulations.

## Phase 46 restore checkpoint extension

Existing target records remain `ARCLITH_TARGET|1` and continue to read only for apply/apply-new transactions. Their historical `BACKUP` value retains its original rollback-copy meaning; a reader exposes no inferred source-backup reference for those records. Restore writes `ARCLITH_TARGET|2` records at the same transaction target directory, with distinct `SOURCE_BACKUP` and `ROLLBACK_BACKUP` opaque 8-character IDs. `SOURCE_BACKUP` is the selected, already-tracked restore input; `ROLLBACK_BACKUP` is the copy of the target as it existed before restore, or `-` when the target was absent. The parser accepts only v2 for restore, validates both IDs, and rejects mixed v1/v2 records for one index. It does not treat either ID as authority to use or delete an artifact.

Restore creates its transaction and `PLANNED` target checkpoint only after target validation and user confirmation, and before creating rollback or staged files. A verified rollback copy is attached while still `PLANNED`; the selected source is recorded from the trusted manifest before any staging. `STAGED` follows successful staging. The transaction advances to `PREPARED` and `APPLYING`; `MUTATION_INTENT` precedes the target rename and `APPLIED` follows a successful rename. `COMMITTING` precedes the managed-state save and `COMPLETE` follows that save. If the target began absent, the rollback reference is `-`; a confirmed applied file is removed only during a rollback guarded by the recorded installed inode and existing path checks.

Checkpoint write failures stop target mutation when they occur before the target rename. An `APPLIED` failure invokes rollback. Rollback writes `ROLLBACK_INTENT` before its target replacement/removal and writes `ROLLED_BACK` only after confirmation. If rollback intent or result cannot be persisted, or the target/manifest outcome cannot be established, the operation returns failure and attempts to leave the transaction `UNCERTAIN`. A failed final transaction `COMPLETE` write does not undo the already-saved target and manifest; they remain in place and the command reports uncertain journal status. Same-filesystem record rename is atomic where supported but no `fsync` is performed. Process termination may leave the last record stale; these checkpoints are not a recovery protocol.

## Phase 47 uninstall and prune checkpoints

The target record layout remains version 1, preserving its existing single opaque `BACKUP` reference and leaving version 1 apply/apply-new records readable. For uninstall/prune it references the verified recovery copy for a target that existed and was eligible for removal. `ALREADY_ABSENT` is a new target state for a target whose absence was checked before ownership cleanup; it has no backup reference and is not interchangeable with `APPLIED` or `NOT_MUTATED`. The writer accepts this state only for uninstall/prune with `ORIGINAL=no`; it is terminal. `NOT_MUTATED` describes an inspectable target preserved because of a conflict or because a failure occurred before deletion.

Each inspectable candidate that passes the operation's safety checks receives `PLANNED` before recovery-copy creation. A successful copy is hashed against the recorded managed hash, its ID is attached while the target remains `PLANNED`, and `STAGED` records that the recovery artifact is ready. After the transaction enters `PREPARED` and `APPLYING`, Arclith saves recovery-copy entries to the manifest before deleting any target. Each present eligible target then follows `MUTATION_INTENT -> confirmed rm -> APPLIED`. Initially missing targets are rechecked immediately before final ownership cleanup and recorded `ALREADY_ABSENT` only if still missing. If one appears after inspection, it is preserved and reported as a conflict. `COMMITTING` precedes removal of ownership entries for deleted and already-absent targets; modified/conflicting targets remain in the manifest. `COMPLETE` follows the final manifest save.

If a checkpoint or backup-registration save fails before deletion, no selected target is deleted. If target deletion is confirmed but `APPLIED` cannot be saved, the existing rollback path runs. During rollback, the transaction enters `ROLLING_BACK`, target `ROLLBACK_INTENT` is persisted before a recovery replacement, and `ROLLED_BACK` follows content verification. If rollback or a required checkpoint cannot be confirmed, the transaction is `UNCERTAIN` when the journal remains writable; recovery artifacts are retained for diagnosis. Prune may finish its safe subset and return its established nonzero status for preserved conflicts; transaction `COMPLETE` means the safe subset and final manifest update finished, not that every candidate was removable. Inaccessible candidates are omitted from target records because their original presence cannot safely be determined. No journal record is automatically deleted, replayed, or used as authority to mutate a target.

## Phase 48 read-only transaction inspection

`config transactions` lists transaction records from `~/.local/state/arclith/transactions/`; `config transactions <id>` inspects one 32-character lowercase hexadecimal transaction ID and its target checkpoints. It reads transaction schema v1 and target schemas v1 and v2 using the existing strict parsers. It checks record filename/ID agreement, file type and private permissions, target index/version uniqueness, target-to-transaction identity, and compatibility between the current transaction state and each target's recorded state. Since the journal stores only each record's latest state, inspection cannot reconstruct or prove every historical transition.

Output uses `COMPLETE`, `IN_PROGRESS`, `UNCERTAIN`, `MALFORMED`, and `INCONSISTENT`. Completed and in-progress labels describe journal structure and recorded state only. Individual inspection prints transaction creation/update times and schema v1, plus target indexes, states, original-presence flags, schema versions, and update times. It omits target paths, backup IDs, and record contents. It labels its source `JOURNAL_ONLY`, record validation, filesystem checks `NOT_PERFORMED`, and snapshot consistency `UNVERIFIED_LOCK_FREE`; these are journal facts only. The command never opens backup contents or follows journal-supplied target paths. It provides manual review guidance and does not recommend blindly rerunning an operation.

Exit status is 0 for a clean requested view, 1 for missing requested records or malformed/inconsistent entries, 2 for invalid command arguments, and 3 for inaccessible or unsafe journal storage. A missing state/journal directory is an empty inventory. Recognized same-directory atomic-write temporary names are skipped; they may be active or left from an interrupted write and are not treated as transaction records. The command does not acquire the mutation lock or create it; a concurrently writing operation can produce a mixed read-only snapshot. Inspecting journal metadata does not prove that a target or manifest mutation happened, that rollback succeeded, or that the record survived power loss. No repair, recovery, replay, rollback, or cleanup is performed.

## Locking and concurrent operations

The helper uses Linux `flock` from util-linux as a kernel-held advisory lock. It fails closed if `flock` is unavailable. The minimum supported environment should be documented; never fall back to an unlocked mutation.

- Acquire one exclusive lock for the canonical `$HOME` deployment state before reading deployment state or target preconditions, and retain it through journal checkpoints, target and manifest changes, rollback, and final journal outcome. Mutating paths are `config apply`, `config apply-new` execution, `config restore`, `config uninstall`, and `config prune`. Dry-run/preview paths need no exclusive lock because they write nothing; their output is an observation that can become stale immediately.
- A writer should validate/create the mode 700 state directory, open a stable mode 600 regular lock file without following symlinks, then request a nonblocking exclusive `flock`. Contention returns a clear “another configuration operation is running” failure before target/state mutation. Lock acquisition errors, unsafe lock paths, and unavailable `flock` fail closed.
- Never unlink or replace the lock file: processes locking different inodes at the same pathname would no longer exclude one another. Kernel lock ownership, not file existence, PID, or age, determines whether a cooperating process currently holds it. A crash releases the OS lock but leaves journal/artifact state uncertain; it does not establish that rollback is safe. Explicit unlock failure is reported; closing the descriptor/process releases the kernel lock, while the journal outcome remains the source of operation status.
- The profile defaults writer is a separate repository-file operation, not a home deployment transaction. Keep it outside this lock unless a later design explicitly defines a repository-level lock.

`config artifacts` must not create a lock or journal. A possible read-only implementation can open an already existing regular lock file read-only and hold a nonblocking shared `flock` while it reads the journal and scans, without writing lock-file bytes; if an exclusive writer holds the lock, it reports “operation active; inventory deferred/incomplete” and does not race the scan. If no lock file exists, the path is unsafe, or shared locking is unavailable, it reports liveness as unknown and must not call a journal interrupted/abandoned. Before adopting even a transient shared lock, verify that the exact `flock`/FD behavior does not create or alter persistent state; the Phase 39 inventory currently has no lock interaction. If strict no-lock inventory semantics are retained instead, it can only report a potentially inconsistent snapshot and must label journal outcomes uncertain. Inventory output never authorizes cleanup or recovery.

## Phase 50 read-only evidence report

`config transactions <id>` now includes the validated transaction timestamps and per-target update timestamps already present in the journal, schema versions, and explicit journal-validation and evidence-source labels. The detailed output identifies filesystem and manifest inspection as not performed and states that the report is a lock-free snapshot. It retains the existing privacy boundary: target paths, backup IDs, and contents are not printed. The manual guidance directs operators to inspect current targets and deployment state and verify backup metadata through `config artifacts`; it asks them to preserve files and not rerun solely from the report.

This report does not read target files, manifests, or backup contents. A structurally valid `COMPLETE` record is historical completion only. A concurrent writer can change records during listing or inspection, and a non-cooperating process can change deployment files at any time. No diagnosis in this command authorizes recovery, repair, replay, rollback, or cleanup.

## Phase 52 diagnostic findings

Inspection emits stable `reason=` codes for diagnostic findings: `UNSUPPORTED_SCHEMA` (record header names an unsupported version), `MALFORMED_RECORD` (required structure or fields are malformed), `INVALID_IDENTIFIER` (stored ID is invalid or does not match the requested record), `INVALID_TIMESTAMP` (a required timestamp fails format validation), `INVALID_TARGET_STATE` (target state is not supported), `INVALID_TARGET_PATH` (target is unsafe or outside its registered component), `IDENTITY_MISMATCH` (target identity fields disagree with their containing transaction or filename), `INCOMPATIBLE_STATES` (valid transaction and target states are not a permitted combination), `INCONSISTENT_CHECKPOINTS` (checkpoint files/references conflict or are internally inconsistent), `RECORD_NOT_FOUND` (requested record is absent), `RECORD_INACCESSIBLE` (record cannot be read), and `UNSAFE_STORAGE` (record type, permissions, or identity do not meet the storage checks). Operational storage failures retain status 3; invalid arguments retain status 2; validation findings retain status 1; clean inspection returns 0. Invalid command arguments do not emit validation reason codes. These codes report only checks actually performed. In particular, a syntactically valid backup ID does not establish backup existence or integrity.

The inspector validates target entries it finds, but the journal has no authoritative expected-target inventory or count. Its output states: “Target enumeration is incomplete by design: this report validates only records found; it cannot prove every target in the original operation was recorded.” A clean validation therefore means all recorded entries passed the checks performed, not that the original target set is complete. Findings and valid-but-incomplete/uncertain transaction states remain distinct.

### Manual investigation checklist

1. Inspect the transaction report and its reason codes.
2. Treat recorded states as historical journal facts, not proof of current filesystem outcomes.
3. Independently inspect current targets, deployment manifests, and backup metadata before deciding what happened.
4. Preserve uncertain targets, backups, and journal records until the evidence is understood.
5. Do not blindly rerun, restore, delete, or reconcile anything based only on a journal state.
6. Record findings and request manual review when evidence is missing, inaccessible, or contradictory.

Inspection remains read-only, lock-free, and snapshot consistency is unverified while writers may be active. It does not reconcile the manifest, inspect backup contents, or prove target enumeration completeness.

1. Completed in Phase 43: define and test the versioned transaction summary record, state transitions, private storage, and atomic replacement behavior. Keep `deployments.v1` unchanged.
2. Completed in Phase 44: add v1 target checkpoint records and integrate apply/apply-new with their existing staging and rollback protocol.
3. Completed in Phase 46: add backward-compatible v2 source/rollback backup references and integrate restore.
4. Completed in Phase 47: integrate uninstall and prune checkpoints, including already-absent outcomes and backup-registration ordering.
5. Completed in Phase 48: add read-only journal listing and individual inspection with schema validation, cross-record checks, and explicit limits.

## Phase 49 recovery policy (design only)

This policy describes what the current evidence can establish. It adds no recovery behavior. A journal checkpoint is a record of the last state Arclith reported; it is not proof that the corresponding filesystem operation happened, that the state survived power loss, or that the filesystem still has that state. `MUTATION_INTENT` and `ROLLBACK_INTENT` record intent only. `APPLIED` and `ROLLED_BACK` mean the command reached its confirmation point at that time. `COMPLETE` means the command recorded completion after its manifest step; it does not attest to current files or later external edits. Inspection is lock-free and can observe a mixed snapshot while a cooperating mutation is active.

### Decision matrix

Every row below requires fresh inspection of the target path without following symlinks, the deployment manifest, and any referenced recovery artifact before a future operator-approved action could even be considered. For a mutation, that inspection must happen under the existing per-home lock after rereading the journal. The existing inspector does not perform these checks. With current capabilities, an interrupted transaction is a manual-intervention case; no state below authorizes automatic replay or rollback.

| Journal evidence | What it establishes / does not establish | Evidence needed before any future recovery action | Current decision |
|---|---|---|---|
| `PREPARING` or `PREPARED`; targets `PLANNED`, `STAGED`, or `NOT_MUTATED` | No mutation intent is recorded for those targets. Does not prove there was no other side effect: apply may already have created parent directories, and temporary or backup files may exist. | Enumerate validated target parents and known artifacts; compare manifest and target contents with current policy. Do not infer safe cleanup from the journal. | Manual review. Preserve artifacts; do not automatically clean staging or backups. |
| `MUTATION_INTENT` with no terminal target checkpoint | Intent was persisted before the operation's mutation. It cannot distinguish a crash just before the mutation from one just after it. | Inspect exact target type, content/hash and parent chain; compare with pre-operation backup where present; verify manifest against its pre-transaction/current contents and validate backup identity/integrity. A match alone may still be user activity. | `UNCERTAIN`; manual intervention mandatory. Never overwrite or delete based on intent alone. |
| Target `APPLIED`, transaction `APPLYING` or `COMMITTING` | The command confirmed that target at its checkpoint boundary. Later targets or final manifest save may not have completed. Does not prove the file remains unchanged. | Inspect every selected target, registered ownership/hash entries, backup artifacts, and manifest. Determine the whole operation set, not just the target shown. | Manual review; mixed transactions are not safely reducible to per-target replay. |
| Transaction `ROLLING_BACK`, target `ROLLBACK_INTENT` | Rollback was requested; the rollback mutation may not have started, may have partly succeeded, or may have succeeded before its result checkpoint. | Compare current target with original backup and expected pre-rollback/current user content; validate backup metadata and contents; inspect manifest and every other target. | `UNCERTAIN`; do not repeat rollback automatically. |
| Target `ROLLED_BACK`, transaction `ROLLED_BACK` | Arclith confirmed rollback at that time. Does not prove that the target or manifest remains restored, nor that every non-target side effect was undone. | Revalidate current files and manifest; distinguish later user changes from transaction results where possible. | Report historical confirmation only; no automatic follow-up. |
| `UNCERTAIN`, malformed, internally inconsistent, or unsupported schema | `UNCERTAIN` records known ambiguity. Malformed/inconsistent/unknown versions cannot be interpreted safely. | Preserve original bytes and artifacts; collect diagnostics without parsing journal values as commands or trusted paths. A newer reader may be needed for an unknown schema. | Manual intervention mandatory; refuse mutation, repair, or state inference. |
| Referenced backup missing, inaccessible, unsafe, or hash/mode-invalid | The journal's opaque ID does not prove that a usable recovery copy exists. | Resolve the ID only through the trusted manifest convention; independently validate canonical target association, regular-file type, owner, permissions, and content hash. | Refuse any action requiring it. Do not substitute another backup by filename similarity. |
| Target missing, changed, inaccessible, unsafe, or now a symlink | Current state cannot be assumed to match the transaction's expected state. Missing does not prove a delete succeeded; changed content can be a user edit. | Establish safe path traversal, ownership, exact content and applicable manifest expectation. If inaccessible or unsafe, no reliable evidence can be obtained. | Preserve and require manual intervention; never overwrite an unknown or changed target. |
| Manifest save failed or manifest is malformed/partially replaced | `config_state_save` writes via a same-directory temporary file and rename, with a saved prior copy for best-effort rollback. Its return status may be ambiguous if a rename wrapper reports failure after replacement or rollback rename fails. It has no fsync guarantee. | Parse the manifest with the strict current parser; compare against transaction intent, ownership hashes, backup references, and any retained `.deployments-old.*` copy. Do not assume either copy is authoritative from its name. | Contradiction or unreadability means `UNCERTAIN`; preserve both copies and require manual resolution. |
| Multi-target transaction with mixed `APPLIED`, `NOT_MUTATED`, `ALREADY_ABSENT`, `UNCERTAIN`, or missing checkpoints | Each record is only a latest per-target checkpoint. Some targets may have changed while others did not; prune may complete its eligible subset while preserving conflicts. | Inspect all targets and manifest entries as one transaction set, including omitted inaccessible prune candidates and retained backups. | No automatic per-target continuation. Manual review of the full set is required. |
| `COMPLETE` while current files or manifest differ | `COMPLETE` is historical command completion, not a current integrity assertion. | Compare current files and manifest to current ownership policy and investigate later changes. | Do not “repair” to match the old transaction. Treat current user state as authoritative until reviewed. |
| Inspection during a writer, stale listing, or files change after inspection | The lock-free inspector may combine record generations; any snapshot can become stale immediately. | A future mutator must acquire the lock and reread/revalidate journal, manifest, targets, and artifacts immediately before acting. Non-cooperating processes remain able to race. | Inspection alone never authorizes mutation. |

Operation-specific evidence limits:

- **Apply / apply-new:** existing targets have opaque references to retained prior-content backups; newly created targets have no original-content backup. A target can be checked against the backup or current managed hash, but the journal does not contain a durable expected hash for the newly installed source or an inode identity that survives restart. Parent directories may be created during preparation. Reverse-order rollback is best-effort and does not make an interrupted sequence replayable.
- **Restore:** v2 distinguishes the selected source backup from the rollback copy. The source can be checked against trusted manifest metadata; the rollback copy can establish prior contents only if the artifact is still valid. If the original target was absent, rollback intends removal, but a later file at that path may be user-created. Manifest restoration is best-effort and a manifest hash mismatch cannot identify who changed it.
- **Uninstall / prune:** `APPLIED` follows confirmed target absence and a verified retained recovery copy was registered before deletion. `ALREADY_ABSENT` records a checked absence, not a deletion. A later absent target does not identify whether Arclith or another actor removed it. Prune can legitimately finish a safe subset and retain conflicted ownership entries; the command may return nonzero despite transaction `COMPLETE`.

### Safety invariants for any future recovery work

1. Treat the journal as untrusted metadata. Independently validate transaction IDs, operation, component registration, target-relative paths, and backup IDs. Never execute journal content or use it as an arbitrary path.
2. Never overwrite, remove, or recreate a target unless its current type, parent chain, owner, and content have been safely established under the per-home lock. If access fails or evidence conflicts, refuse.
3. Before using a backup, resolve it through trusted manifest data and verify its identity, target association, regular-file type, ownership, restrictive permissions, and content hash. A valid backup proves its bytes, not that replacing today's target is appropriate.
4. Do not silently discard user changes made after the transaction. If current content differs from both a verified original backup and a verifiable transaction result, preserve it and require manual intervention.
5. Never delete or rotate a journal, backup, temporary file, or manifest recovery copy as an implicit recovery step. Preserve evidence and report exact safe-to-inspect locations only after validating that those paths are generated by Arclith.
6. Treat contradictory, missing, inaccessible, malformed, unsupported, or stale evidence as `UNCERTAIN`. Do not convert uncertainty to success by guessing.
7. Any future mutation must acquire the existing per-home lock, reread all records and state under that lock, revalidate immediately before each filesystem action, and persist intent before mutation and outcome only after verification. The lock coordinates cooperating Arclith processes only.
8. Keep filesystem changes, manifest replacement, and journal writes as separate failure domains. A success or failure in one does not imply the same result in another; atomic rename does not guarantee power-loss durability.
9. Design retries as explicit new, auditable decisions. Record what was verified and what action was taken so a repeated request can detect already-applied work and stop on changed evidence; never replay a stale intent blindly.
10. Refusal must preserve all artifacts and provide actionable diagnostics, including which evidence was unavailable or contradictory and which manual checks are needed, without exposing file contents or treating sensitive paths as trusted instructions.

The current architecture cannot enforce all these rules: journal records lack content fingerprints for the intended post-mutation target and a complete immutable event history; inspector reads are unlocked; the advisory lock cannot stop non-cooperating writers; manifest and filesystem changes are not one atomic transaction; and no fsync is performed. Even adding hashes or event records would not alone prove causation, prevent subsequent edits, or make power-loss recovery safe.

### Recovery approach comparison and recommendation

| Approach | Correctness and data-loss risk | Races, retries, and complexity | Assessment |
|---|---|---|---|
| A. Manual-only guidance from read-only inspection | Lowest risk of an automated overwrite, but places investigation and any repair decision on the operator. | No mutation race is introduced by Arclith; the operator can still act on stale observations, so instructions must require reinspection and backups. Lowest implementation and test burden. | **Recommended for the current evidence.** Inspection is diagnostic only and must not label a transaction recoverable. |
| B. Explicit operator-approved recovery for narrow cases | Could be acceptable only for a case with independently verifiable target, manifest, and backup evidence; confirmation does not make incomplete evidence trustworthy. | Requires lock-held revalidation, a documented allowlist of cases, idempotent action records, fault injection at every mutation boundary, and refusal on any drift. Medium-to-high complexity. | Consider only after policy review and a read-only evidence classifier can identify a genuinely bounded case. Current journal lacks enough evidence to safely authorize a general rollback. |
| C. Automatic recovery during normal commands | Highest risk: an ordinary command can overwrite later user changes based on a stale or ambiguous record. | Startup races, repeated attempts, partial failures, schema evolution, and testing surface are largest; a failure during recovery creates another interrupted transaction. | Not recommended. No reliable basis exists to choose a recovery action automatically, and it is not needed for normal command execution. |

### Future test gates

Before any recovery mutation is considered, add isolated temporary-home failure-injection tests that terminate or fail before and after every transaction and target checkpoint, filesystem replacement/deletion, rollback action, and manifest rename. Include missing, corrupt, inaccessible, symlinked, and mismatched backups/manifests; current user edits after interruption; targets absent or replaced by another inode; multi-target mixed outcomes; journal failures during rollback; cooperating lock contention; and non-cooperating changes detected by immediate revalidation. Repeat the same approved request to prove idempotency and prove that changed evidence causes refusal. Every refusal test must assert that targets, manifest, backups, and journals remain byte-for-byte unchanged. Add crash/power-loss claims only if a separate durability design and suitable test environment support them; command wrappers are not power-loss tests.

### Phase 50 recommendation and non-goals

Keep Phase 50 read-only: improve recovery diagnostics or provide a manual evidence-gathering runbook, clearly separating journal classification from verified filesystem observations. Have the recovery policy reviewed before proposing any operation that changes files. If review later supports operator-approved recovery, first define one narrow case, the evidence proving its preconditions, its retry identity, and refusal conditions; then implement it behind explicit confirmation with isolated failure-injection gates. Do not add automatic startup recovery.

This design does not implement recovery, replay, repair, rollback, journal cleanup, a schema change, a new transaction state, or a claim of crash or power-loss recovery. Open questions for policy review include how an operator distinguishes a later user edit from an interrupted command's result, whether any existing recovery case has sufficient causal evidence, and what diagnostic artifact retention policy is appropriate without automatic deletion.
